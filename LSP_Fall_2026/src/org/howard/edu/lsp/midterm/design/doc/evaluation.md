The CourseRegistration class has a few major object-oriented design issues, mainly because it tries to do way too much all in one place. Its registerStudent() method handles calculating tuition, applying discounts, printing info, writing records to a file, sending confirmation messages, and logging timestamps. Packing all of this into a single method makes the code really hard to maintain—if just one of those processes changes, you have to edit the whole method.

On top of that, all five fields are marked public. This means any other class can change student details, course info, or credit hours directly without any validation, which completely breaks encapsulation and opens the door for invalid data. Making these fields private with proper getters and setters would fix this.

The class is also way too tightly coupled to specific tools. It directly uses FileWriter to save data and uses basic print statements to fake sending emails. If the university ever switches to a database or a real email service, this entire class would have to be rewritten.

Overall, this design breaks several of Arthur Riel’s design heuristics, like keeping related data together and avoiding classes with unrelated jobs. CourseRegistration tries to be a manager, accountant, file saver, email sender, and logger all at once. It also handles errors poorly by just printing stack traces instead of handling them properly.

A much cleaner design would split these jobs into separate classes—like RegistrationService, TuitionCalculator, RegistrationRepository, and ConfirmationService. Giving each class one clear responsibility makes the overall code much more flexible, easier to test, and easier to update later.
