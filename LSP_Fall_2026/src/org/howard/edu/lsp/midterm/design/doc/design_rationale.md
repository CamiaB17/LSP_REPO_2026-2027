# Design Rationale for Evolving Requirements

The proposed design supports different storage options through the `RegistrationRepository` interface. `FileRegistrationRepository` can save records to a local file, while `DatabaseRegistrationRepository` can save records to a database. The application can select the appropriate implementation based on the deployment environment without changing the main registration process in `RegistrationService`.

The confirmation requirement can be supported through the `ConfirmationService` and separate email and text confirmation implementations. The system can select the appropriate communication method based on its configuration and the student's available contact information. These changes allow the system to support additional storage and communication options without placing their implementation details inside `RegistrationService`.

One important design decision is that `RegistrationService` coordinates the process but does not directly perform file or database operations. The repository is responsible for storage because it separates persistence details from registration logic. This reduces coupling and makes it easier to test registration processing independently of the storage method. The same principle applies to confirmation delivery: the service requests a confirmation without needing to know the details of sending an email or text message.
